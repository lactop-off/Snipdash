# AI 駆動開発プロセス（エンジニアチーム）

Snipdash を Claude Code のサブエージェント（`.claude/agents/`）でチーム開発するための役割分担とワークフロー。各エージェントは**独立コンテキスト**で動くため、引き継ぎは必ず**成果物ファイル**で行う。

## ロール

| ロール | エージェント | 主担当フェーズ | できること（ツール） |
|---|---|---|---|
| PM / プロダクトオーナー | `pm` | 要件定義・最終受け入れ | 文書作成・調査（コードは書かない） |
| UI/UX デザイナー | `designer` | 基本設計（画面・UX・Iconify指定） | 文書作成・調査（コードは書かない） |
| テックリード / アーキテクト | `tech-lead` | 詳細設計・設計の実現性レビュー | 文書作成＋読み取り系チェック（`cargo check` 等） |
| コーダー | `coder` | 実装＋単体テスト | Edit/Write/Bash（実装一式） |
| QA エンジニア | `qa` | 設計レビュー・コードレビュー・テスト | Bash で**実行して検証**＋テスト記述 |

> QA は**独立・批判的**な品質ゲート。実装者の自己承認に頼らず、QA が PASS を出すまで前工程へ戻す。

## ワークフロー（ゲートとループ）

```
[人間] 機能の依頼
  → 要件定義 (pm)            → 要件定義.md（受け入れ基準/DoD を含む）
  → [人間 承認ゲート ★]       ← 要件はここで人間が承認してから次へ
  → 基本設計 (designer)       → 基本設計.md
  → 設計レビュー (qa + tech-lead)   NG → 再設計(designer)  ←ループ
  → 詳細設計 (tech-lead)      → 詳細設計.md（実現性 verdict 付き）
  → 設計レビュー (qa)               NG → 再・詳細設計        ←ループ
  → 実装 (coder ＋ 単体テスト)
  → コードレビュー (qa)              NG → 再実装(coder)      ←ループ
  → テスト (qa: 実行＋実機検証)        NG → 再実装(coder)      ←ループ
  → [人間 最終受け入れ ★]
```

- **人間チェックポイント（★）は必須**：要件承認と最終受け入れは人間（あなた）が行う。AI に要件を完全自走させない。
- **ループ上限**：同一ゲートの差し戻しは **最大3回**。収束しなければ理由を添えて**人間にエスカレーション**（無限ループ防止）。
- 設計レビューは QA（要件充足・品質）＋ tech-lead（技術的実現性）の二観点。

## ハンドオフ成果物

1機能ごとに `docs/work/<feature-slug>/` を作り、各フェーズが追記/更新する：

| ファイル | 作成者 | 内容 |
|---|---|---|
| `要件定義.md` | pm | ゴール / スコープ / FR / **受け入れ基準(DoD)** / 制約 / 人間への質問 |
| `基本設計.md` | designer | 画面・状態・操作・配色・**lucideアイコン名**・ja/en コピー・a11y |
| `詳細設計.md` | tech-lead | 変更ファイル / スキーマ影響 / コマンド・権限 / テスト計画 / リスク |
| `コードレビュー.md` | qa | 設計・コードレビューの verdict と指摘 |
| `テストレポート.md` | qa | テスト実行結果・実機検証（スクショ含む）・verdict |

> 詳細は `docs/work/概要.md`。

## 受け入れ基準 / Definition of Done

PM が要件定義時に客観的・検証可能な形で明文化する。最低限つねに含める：
- `pnpm typecheck` が通る
- 該当する `cargo test` / SDK vitest が通る
- `pnpm --filter @snipdash/desktop build:vite` が通る
- 仕様どおりの**実挙動**を QA が実機（Playwright 等）で観察して確認
- Rust⇄TS の lockstep・i18n(ja/en)・最小権限・デモパス維持などの制約を満たす

## オーケストレーション（誰が回すか）

- サブエージェントは原則 **1 階層**（サブからサブは呼べない）。フェーズの順序制御は**メインの Claude**が担う。
- 使い方：機能を依頼すると、メインの Claude が各 `description` を見て適切なエージェントへ委譲する。明示する場合は「`pm` で要件定義して」「`qa` でテストして」のように指定。
- 反復オーケストレーションを自動化したい場合は、後から `/pipeline` スラッシュコマンドやワークフロー化も可能（要相談）。

## チューニング（任意）

- **モデル**：判断重視（pm / designer / tech-lead / qa）は上位モデル、機械的な実装（coder）は軽量モデルに。各 `agents/*.md` の frontmatter に `model:` を追加して出し分け（未指定だと親=セッションのモデルを継承）。
- **ツール**：各ロールは最小権限。PM/デザイナーはコード編集不可（read+write+web）、QA は実行可（Bash）に絞ってある。

## 共通規約

プロジェクト規約は `CLAUDE.md` に集約（Rust⇄TS lockstep、スキーマ移行、信頼境界、i18n、アイコンは Iconify=lucide のダウンロード SVG をインライン等）。全エージェントはまず `CLAUDE.md` を読むこと。
